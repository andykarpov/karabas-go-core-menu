# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

The boot menu core of the Karabas Go, Mini and Mini G boards: Xilinx Spartan-6 XC6SLX25, ISE 14.7 (XST). The core draws its own menu (`docs/PLAN.md`): a VexRiscv rv32im soft CPU (`menu_soc`) draws the core list and the Setup pages in the look of the old FT812 menu, the same on all three boards. The firmware has no boot menu any more (Ф4): it loads the core and its ROMs and serves the CPU over link v2 RPC. Three tops: `src/rtl/karabas_go_top.v` (VGA through the video DAC, the FT812 video on it too), `karabas_mini_top.v` and `karabas_minig_top.v` (HDMI, the FT812 video on HDMI too). The defines HW_ID1 (Go), HW_ID2 (Mini), HW_ID2 + HW_ID3 (Mini G) are set in the `.xst` files.

- The CPU: `src/rtl/soc/menu_soc.v` (VexRiscv of karabas-go-core-doom, I$ / D$ 4K, `rtl/soc/vexriscv/VexRiscv.v`) on clk_cpu 75 MHz. Its program `src/roms/menu.bin` (built from `src/sw`) and the sounds `src/roms/sounds.bin` are ROMs of `boot.kg` (`core.json` `roms`: address 0 and 0x200000); the firmware loads them into the SRAM (LOAD kind 0, caps bit 4: the core drives LD_READY) and the CPU is held in reset until the load has ended. The code runs from the SRAM behind the caches. The memory map and the MMIO registers are in the header of `menu_soc.v` and in `src/sw/mmio.h`.
- The SRAM (both 2M x 8 chips as one 2M x 16, `menu_sram.v`): the program, the data, two frame buffers of 800 x 600 x 8 bpp at 0x300000 and 0x380000, the sounds. `menu_sram` clears all of it after the PLL lock and again before a core starts: the CPU writes the `CORES LAUNCH` request and the MMIO LAUNCH register, the CPU stops for good, the SRAM is filled with zeros (84 ms), then the request goes to the firmware. Every core starts with clean memory. `sram_clear.v` and `vga_sync.v` are still in the tree but not in the build.
- The video: `rtl/vga/menu_video.v` scans the shown frame buffer out at 800 x 600 60 Hz (clk_sys, the timing of the old `vga_sync`), a palette bank per buffer (a picture is drawn into the hidden buffer with its own colours, then shown); `menu_compose.v` blends it (alpha 0..15) over the FT812-style gradient (the `[ft812]` colours of karabas.ini, written by the CPU); `menu_bg.v` is the glow shown while the CPU shows nothing. The bitmap OSD of link v2 (`kg_l2_osd_overlay`, scale 2) is on top of it all (the firmware's messages).
- RPC: `kg_l2_rpc` of modules in `kg_mcu2` (target 08, `ENABLE_RPC`, `RPC_SERVICES` 16'h000F = SYS, CFG, CORES, HID), the mailbox at MMIO 0x80002000 (`src/sw/rpc.c`). The spec is karabas-go-firmware `docs/link_v2.md` 5.9; the design notes and the later services are in `docs/RPC.md`. Until the release the modules and the firmware are on their `feature/rpc` branches.
- The ESP8266 (`rtl/uart/esp8266.vhd`): its uart goes to PORT 1 of `kg_mcu2` (the passthrough to the MCU), except while the CPU has it (MMIO ESP_OWN: Setup > Wi-Fi, NTP sync); then the MCU gets nothing.
- MIDI: `rtl/soc/menu_midi_mux.v` merges the notes of the CPU (MMIO MIDI, the key click) with the thru of a USB MIDI keyboard (PORT 2 of `kg_mcu2`, caps bit 9) at whole messages into `kg_midi_tx` on `MIDI_TX` (31250 baud, the SAM2695).
- Sound: `rtl/soc/menu_sound.v`, two PCM channels (raw signed 16-bit mono in the SRAM) at 48 kHz, added with saturation to the audio: on the Go the PCM5102 gets the menu sound only (no ADC here); on the Mini the sigma-delta DACs and HDMI get it with the ADC (`i2s_transceiver`); on the Mini G the PCM5102 and HDMI with the ADC.
- The SD slot of the FPGA is passed through to the MCU (`kg_mcu2` `ENABLE_SD2`: chip select `MCU_SPI_SD2_CS_N` on the Go, `MCU_IO[2]` on the Mini / Mini G): the firmware shows it to the PC as the second USB drive (`msc2`, BTN2 held 2 s, `buttons` of the json). SD_CLK: on the Go `SD2_SCK` of `kg_mcu2`, on the Mini the `MCU_SCK` pad (local routing, not a clock pin before rev G), on the Mini G the IBUFG output of MCU_SCK, as the FT812 SCK (a BUFG cannot drive a pad).

The board modules (MCU link, memories, clocks, DACs, OSD, HDMI) come from the git submodule `modules/` ([karabas-go-modules](https://github.com/andykarpov/karabas-go-modules), shared by the Karabas Go cores; clone with `--recursive` or run `git submodule update --init`). A change to them is made there and taken here by updating the submodule commit. Its `CLAUDE.md` and `docs/PLAN.md` have the rules (Verilog-2001 for XST, tests, checks of LUTs and timing).

This core is the loader of every other core: a broken build leaves the board without a menu. Test in simulation and on the hardware of the three boards before a release. Until the release a test build goes to the card as a separate core `menutest.kg` (type osd, CORES in its HELLO; a boot type core cannot be started by AT load), never over the real `boot.kg` (user rule).

## Build

- `cd src && make` builds the three boards (`make go`, `mini`, `minig` one of them; `make minig-xst`, `-impl`, `-core` one step; `make minig-report` the utilization and timing of the last build, `make minig-coremode` the second timing run of the Mini / Mini G, see Timing). It runs the ISE command-line flow and sources `/opt/Xilinx/14.7/ISE_DS/settings64.sh` (`ISE_SETTINGS=` to change it). The boards share `xst/` and `_ngo/` in `src/`, so they are built one after the other; a board takes a few minutes.
- Inputs per board: `karabas_<board>.prj` (the source list, the shared modules as `"../modules/rtl/..."`), `.xst`, `.ucf`, `.ut`. There is no ISE GUI project (`.xise`); the `karabas_*_top.*` files in `src/` are leftovers of it, not used. The Makefile has the map / par options (those of tsconf). The map cost table is per board, `MAP_T_<board>` (the Go 1, the Mini 2, the Mini G 3): when a build misses a constraint by a placement (a path without logic and a long route), try another (2...5) before changing the design.
- `core` packs `karabas_<board>.bin` with `core.json` (one file for all boards: the common keys, `boards` for what differs; kgo2, karabas-go-tools `docs/kgo2.md`) and the ROMs `roms/menu.bin`, `roms/sounds.bin` into `boot.kg` (`make <board>-core`: `make_core.py core.json boot.kg --boards <board>` puts that board's bitstream in) with `make_core.py`. The stamp depends on the `.bin` and `core.json` only: a new `menu.bin` alone does not repack `boot.kg`. The `.bin`, `.kg` and `roms/*.bin` files are committed as the release; `build` of the json is `date +%y%m%d%H` of the release build.
- The CPU program: `make -C src/sw` (xPack `riscv-none-elf-gcc`, `XPACK=` the bin directory, default `~/opt/xpack-riscv-none-elf-gcc-15.2.0-1/bin`; `-march=rv32im`, newlib-nano, `link.ld`) writes `src/roms/menu.bin`. `make fonts` / `images` / `sounds` regenerate the committed `fonts_gen.h` (Noto Sans, 4 bpp), `images_gen.h` and `sounds_gen.h` + `roms/sounds.bin` (from `sw/assets/ft_bitmaps.h`, the pictures and start sounds the firmware had).
- The `osd` items of the json (Reset, Global Reset) are left from the old core: the tops leave `SW` of `kg_mcu2` open.

## Timing

- Clocks (the tops), one PLL from CLK_50MHZ (VCO 450 MHz): clk_cpu 75 MHz (/6, out 2: the CPU, the SRAM, `kg_mcu2`, the ESP and MIDI uarts, `menu_sound`), clk_sys 40.91 MHz (/11, out 0: the pixel clock, the scanout of `menu_video`, `menu_compose`, the OSD overlay, the audio and DACs, HDMI), on the Mini / Mini G clk_8 8.18 MHz (/55, out 1: FT_CLK_OUT and the base of DCM_CLKGEN of `hdmi_pll`), MIDI_CLK 12.16 MHz (/37) on out 1 on the Go and on out 3 on the Mini. The PLL output of clk_sys has no BUFG in `kg_pll`: the BUFG is in the top and on the Mini / Mini G the same output feeds the BUFGMUX of `hdmi_pll`.
- HDMI (`rtl/hdmi`, the code of tsconf): `hdmi_top.v` (the FT812 / menu mux, audio, the crossings into the pixel clock) around zhdmi (`hdmi_tx` of modules, `OUTPUT_REG(1)`: the encoder -> serializer path); `hdmi_pll.v` measures FT_CLK (`freq_counter.vhd`) and programs DCM_CLKGEN (clk_8 x M) for the FT modes, up to 64 MHz. The FT812 video goes through `kg_async_fifo` written on the falling FT_CLK; what goes from clk_sys to the pixel clock leaves registers on the falling clk_sys.
- The three ucf have the same timing block (the end of each file, then the parts of the board): PERIOD on CLK_50MHZ (derived onto the PLL outputs), the groups TG_CLK_SYS on the BUFG `clk_sys` (on the PLL output net it leaks through the BUFGMUX into the pixel clock) and TG_CLK_CPU on `pll_clk<2>`, TS_CPU_TO_SYS / TS_SYS_TO_CPU (13.3 ns DATAPATHONLY: no common period, the paths are toggles, the line buffer and palette RAMs and settings held stable), TS_SRAM_OUT / TS_SRAM_IN (8 / 4 ns, the IOB flip-flops of `menu_sram`, a two-clock read of the 10 ns SRAM), TS_CLK_MCU 32 MHz, DATAPATHONLY bounds for the asynchronous crossings (MCU_SCK <-> clk_sys and TS_MCU_TO_CPU / TS_CPU_TO_MCU; on the Mini / Mini G FT_CLK <-> clk_sys / pixel clock, clk_sys -> pixel clock), FT_CLK with its PERIOD (80 MHz) and the DCM_CLKGEN pixel clock (64 MHz), a TIG on the KEEP net `mux_sel` of the BUFGMUX; TS_SER_D (Mini / Mini G) bounds the TMDS words -> the serializers at the menu mode, which the FT-mode PERIODs time loosely. On the Go the VGA outputs are IOB registers bounded by TS_VGA_OUT (V_CLK is ~clk_sys). Each exception is explained there; do not TIG paths that are real.
- `make <board>-coremode` (Mini, Mini G) runs trce again without the FT-mode constraints (`src/pcf_core.py`): the clk_sys -> pixel clock paths with the setup and hold of clk_sys, the mode of the menu. Run it after every build of the Mini / Mini G.
- MCU_SCK of the Mini G goes through IBUFG + BUFG; the SCK of the FT812 SPI and SD_CLK take the IBUFG output.
- No clocks from logic and no latches: check "Clock Information" of the `.syr`.

## Simulation

- `src/sim/soc/run_soc_sim.sh` (Verilator): `tb_menu_soc`, `menu_soc` + `menu_video` + `menu_compose` + `kg_l2_rpc` with the real program against a model of the MCU (the core list over RPC, keys, LAUNCH) and of the ESP; runs: keys, mouse, sound, Setup, Wi-Fi, each prints `tb_menu_soc: 0 errors` and writes a frame (`*.ppm`). It runs `make -C ../../sw` first, which rewrites `src/roms/menu.bin`.
- `src/sim/midi/run_midi_sim.sh` (iverilog): `tb_midi_mux`, the keyboard and CPU streams of `menu_midi_mux`; prints `tb_midi_mux: 0 errors`.
- `src/sw/host/run.sh` (gcc on the host): the drawing code of the menu with a fake firmware (`host/host.c`), the frames of the screens as PNG in `src/sw/host/out`. For quick looks at a screen; the UI needs the user's approval on frames.
- `src/sim/run_hdmi_sim.sh` (ISim): `tb_hdmi_top`, the menu video at 40.9 MHz and the FT812 through `hdmi_pll` and the fifo, every pixel where it enters `hdmi_tx`, the audio samples. Prints `tb_hdmi_top: 0 errors`.
- Left from the old menu, they do not test the build: `run_eq_sim.sh` (`kg_osd_overlay` against the old `overlay.vhd`), `run_mcu_sim.sh` (`kg_mcu` link v1 against the old `mcu.vhd`; the tops use `kg_l2_osd_overlay` / `kg_mcu2` now) and `run_sram_sim.sh` (`sram_clear.v`, replaced by the clear of `menu_sram`).
- The tests of the shared modules (`kg_l2_rpc`, `kg_mcu2`) are in `modules/sim` (`run_all.sh`).

## Layout

- `src/rtl/karabas_*_top.v`: the boards: PLL, `kg_mcu2`, `menu_soc`, `menu_video`, `menu_bg`, `menu_compose`, `kg_l2_osd_overlay`, `esp8266`, `menu_midi_mux`, the DACs, HDMI.
- `src/rtl/soc`: `menu_soc.v` (CPU, MMIO, loader, LAUNCH), `menu_sram.v` (SRAM, the clear), `menu_sound.v`, `menu_midi_mux.v`, `vexriscv/` (the generated VexRiscv and its config). `src/rtl/vga`: `menu_video.v`, `menu_compose.v`, `menu_bg.v`. `src/rtl/hdmi`: `hdmi_top.v`, `hdmi_pll.v`, `freq_counter.vhd`. `src/rtl/uart`: `esp8266.vhd`, `uart_rx.vhd`, `uart_tx.vhd`. `src/rtl/adc`: `i2s_transceiver.vhd` (the ADC of the Mini / Mini G).
- `src/sw`: the CPU program: `main.c` (the loop), `browser.c` (the core list, autoload), `setup.c` / `settings.c` (Setup and the karabas.ini settings over RPC CFG), `wifi.c` / `wifi_page.c` / `esp.c` / `esp_update.c` / `ntp.c` (Wi-Fi and NTP over the ESP uart), `pad_page.c` (Gamepad, HID learning over RPC), `ui.c` / `gfx.c` / `fonts.c` (drawing), `sound.c`, `rpc.c`, `crt0.S`, `link.ld`, `syscalls.c`; `lib/` files of the firmware `lib/common` used as they are (a change goes to the firmware first); `assets/`, `tools/` (the generators), `host/`.
- `src/roms`: `menu.bin`, `sounds.bin` (the ROMs of `boot.kg`).
- `src/sim/ref`: the old code (new_hdmi_pll d31dec0) of the old equivalence tests.
- `docs/PLAN.md` (goals, decisions, phases, status), `docs/RPC.md`, `docs/img` (the frames compared with the FT812 menu).
